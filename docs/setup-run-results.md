# Setup, run and results

The workflow is `catmodel setup` → `catmodel run --setup …` → `catmodel results`. A setup freezes scientific inputs, execution controls and selected evidence. A run simulates the eventual loss from incidents that originate in one year, and saves an immutable capture with initial results. The results commands replay, reweight, summarize or export that capture without simulating. Every command's `--output` names a new file or directory; an existing path is refused, never overwritten.

`catmodel.contracts.run_setup.RunSetup` is the setup object. Its `scope` (`RunScope`) declares the study dates, capability scales, roster and populations, and its `EvidenceSet` holds the evidence records and selected original bytes, including elicited judgments with their provenance. Joint states, conditional contexts, alternatives and contracts are resolved executable inputs, whether they come from a fit, a judgment or a stipulation. The [methodology](../methodology.md) describes the calculation, and [incident accounting](incident-accounting.md) the loss views, lab loss and insurance terms.

## Frozen workflow

```sh
uv sync --frozen --group dev
uv run --frozen catmodel setup build \
  --spec config/setups/stipulated-campaign/setup.json \
  --plan config/setups/stipulated-campaign/plan.json \
  --evidence config/setups/stipulated-campaign/evidence \
  --setup-id stipulated-campaign --output /tmp/campaign-setup
uv run --frozen catmodel setup inspect --setup /tmp/campaign-setup
uv run --frozen catmodel run --setup /tmp/campaign-setup --output /tmp/campaign-run
uv run --frozen catmodel results replay --setup /tmp/campaign-setup \
  --capture /tmp/campaign-run/capture --output /tmp/campaign-replay
```

This example's inputs are stipulated, so its numbers show the software at work and measure nothing. The [golden Poisson example](../config/setups/golden-poisson/README.md) is the smallest end-to-end run whose results can be checked by hand, as `tests/test_golden_poisson.py` does. The installed-wheel acceptance check ([TESTING.md](../TESTING.md)) runs this example and `config/setups/stipulated-conditional` from an installed wheel.

| Directory | Holds |
|---|---|
| Setup (`setup build`, `setup import`) | `setup-manifest.json` (the setup ID, code provenance and file checksums), `setup.json`, one file in `alternatives/` for each arm that overrides laws, `execution-plan.json` and any selected `evidence/` bytes |
| Run (`run`) | `capture/` (`run-capture.json` and the native draws), `results.json`, its diagnostics file `results.diagnostics.json` and `tornado.svg` |
| Replay (`results replay`) | `results.json` and its diagnostics file ([results files](#results-files)) |
| Summary (`results summary`) | `summary.md` and `summary.csv` ([readable summary](#readable-summary)) |
| Export (`results export`) | `export.json`, the capability artifacts and copies of the setup, capture and results |

A setup's identity is the SHA-256 of its manifest, and a capture's is its `content_sha256`. Neither records when it was made, so the same inputs built or run again with the same code and environment give the same setup and capture, byte for byte.

**Authored inputs.** `setup build --spec` reads one flat JSON object whose keys are the setup's fields, with every value written in place (the inline layout). Authored setups take annual rates, not probabilities: an annual `P(N ≥ 1)` = p identifies the rate `−log(1 − p)` only under a conditional Poisson model, so a study that holds probability evidence authors the rate explicitly.

**Saved setups.** A saved `setup.json` (schema 1) holds the same object as canonical JSON, with two changes. The records that many laws repeat (`severity_laws`, `mark_kernels`, `public_trajectories` and `texts`) are stored once, in tables keyed by their SHA-256. Each alternative's `overrides`, the laws it puts in place of reference laws, holds the name of the alternative's file, `alternatives/<SHA-256 of its bytes>.json`, or null. Import can therefore write, and a run read and validate, one arm at a time, so their memory does not grow with the number of arms. `setup build --spec` refuses a saved `setup.json`. The scientific fingerprint is the canonical sorted-key JSON digest of the inline encoding without its disclosure prose (the `title`, the `limitations` and each alternative's `description`), so rewording them keeps the fingerprint.

**Execution plan.** `execution-plan.json` freezes the `required_arms` and `reference_arm`, `requested_views`, `simulations` (starting years per state), `seed`, `comparison_requirements` and `numerical_controls`: the work allowances (`NUM-BUDGETS`), `event_batch_size` (default 65,536), `small_events` (`NUM-SMALL-EVENTS`) and `tail_gate` (`NUM-TAIL-GATE`). Building or loading a plan refuses an unknown or malformed control, and a `tail_gate` whose driver `views` are not all among `requested_views`. A state over a work limit stops the run without a capture; no rate, cluster or severity is clipped to fit. Each comparison requirement names its family, arm, scenario scope, held-fixed quantities and status (`required`, `unavailable` or `inapplicable`).

**Code provenance.** A setup's manifest, a run's `producer_provenance` and each result's `reducer_provenance` identify the running code by its `tree_state`: `clean`, `dirty` or `unknown` for a Git checkout, whose HEAD is the `commit`; `installed` for code outside a checkout, which the installed `version` identifies; and `asserted` for a commit that a caller of the Python API gives as `code_commit`, recorded without inspection. Every record also gives the numerical environment.

**Workers.** The global option `catmodel --workers N` sets the worker processes of `run`, `results replay`, `results export` and `setup import`. No number or identity depends on N, which `results.json` records under `execution_context` ([runbook](../runbook.md#choosing-the-worker-count)).

**Replay.** For `catmodel results replay`, `--level` adds tail levels to the defaults, 0.9, 0.99, 0.995, 0.996 and 0.999, and `--weights <file.json>` gives target weights for the captured states, as a JSON object in one of two shapes:

- Every declared state ID with its target probability, which every arm takes. This shape applies where no required arm authors its own state weights (an alternative's `state_weights`); elsewhere it is refused, unless it repeats the setup's weights.
- Every required arm ID with such an object, which gives each arm its own target. A public study's setup needs this shape, because its reweighting arms, which include every `public_forecast` and `model_pooling_leave_one_out` arm, author their weights.

Without `--weights`, each arm keeps the setup's weights: its own `state_weights` if it authors them, and otherwise the joint states' `weight`. Either shape refuses weight on a state outside an arm's frozen support: public-study import has each arm simulate only the states it weights, so the no-progress trajectory node is outside the reference arm's. When the target weights differ from the setup's, the exhibits that rest on the setup's weights are reported `unavailable`: `trajectory_quadrature`, `capability_scenarios`, `frequency_estimate`, `hierarchy_pool`, `large_loss_anchor` and the EAL parameter band. Changed ownership, occurrence grouping or another unretained observable needs a new run. The reducer code, tail levels, target weights and atom conventions determine a results identity; producer provenance stays unchanged.

**Statistic statuses.** Each available view gives every headline statistic a status in `statistics`, with a reason unless available:

- `available`.
- `withheld`: the run cannot support the value, which keeps its point estimate. VaR and TVaR are withheld when the tail convergence gate has not converged them (`NUM-TAIL-GATE`; [methodology](../methodology.md#numerical-execution-and-outputs)).
- `unavailable`: the law gives the statistic no finite value. An infinite mean leaves EAL and TVaR null and `unavailable`, while quantiles and probabilities may remain available.

VaR, TVaR and occurrence (OEP) statistics are reported as illustrative: they depend far more than the EAL on tail shapes, caps and the conditional independence of scenarios, which are set by judgment ([limitations 3](limitations.md#3-tail-shapes-caps-and-spread-factors-are-judgments) and [5](limitations.md#5-scenarios-are-conditionally-independent)).

Undefined or overflowing relative effects are null with reasons; absolute effects remain. An effect between analytic EALs has no sampling error and so no `half_width`.

**Coverage and status.** Each result has a `coverage` table of the views, comparison families and setup populations it includes or leaves out, with reasons, and one ordered `limitations` list: the setup's limitations, the run's gaps, then model-wide items linked to the [limitations list](limitations.md). A result's `status` is `complete` only when `coverage.comparisons.status` is `complete`: every required alternative arm was captured and compared with the reference in its requested views, and every comparison requirement resolved as available or inapplicable. Otherwise it is `partial`, which describes comparison coverage and not a failed run: the reference metrics and the executed comparisons remain valid. An empty comparison inventory reports `not_requested`, and one that holds only reasoned inapplicability reports `inapplicable`; both leave the result `partial`.

Context-bound results are always `partial`: `setup import --run-directory` requires only the reference arm, and `setup import --study` executes its [default comparison set](#context-bound-comparisons) and leaves the other families unavailable. Each view's ranking is `available`, `unavailable` (comparison coverage in the view's scope is incomplete, or a finite effect is missing), `not_requested` (no required alternative arm is in the view's scope) or `inapplicable`. `rankings_available` requires a `complete` result with at least one available ranking and no unavailable one. The [runbook](../runbook.md#6-reporting-and-failures) says what to read before quoting a number.

## Results files

A results file `<name>.json` has its diagnostics file `<name>.diagnostics.json` beside it. The two files hold one report, a `NativeResults`: `results.json` holds the headline, the sections of `HeadlineResults`, and the diagnostics file holds the exhibits, the sections of `ResultsExhibits`, which are report-only analyses of the same capture, and the per-arm view diagnostics. The headline is the layout to build on. It is small, 315 fields in 66 record types, and `tests/test_results_schema.py` pins its size: a new report-only analysis is added to the exhibits. The JSON Schemas in `contracts/results/` are the reference for every field of both files ([below](#results-file-versions)).

`catmodel.results.results_file.load_results` reads the headline and, with `diagnostics=True`, the whole report. A headline read alone refuses a request for an exhibit or the view diagnostics, and names the diagnostics file.

`results.json` holds the headline:

- `schema_version` (below) and `study`, what the result describes: the setup, scope and title, the scope's dates, the scenarios, the monetary bases, the named entities and the deployments.
- `analysis_sha256` and `analysis_spec`, the result's identity; `status`, `coverage` and `limitations`.
- `arms`: each arm's statistics by view, with their statuses, and each view's `eal_reconciliation` of its simulated years with its analytic EAL. Where a sample is left out of the views that count the lab's own loss, the lab-loss views and the gross views (`POOL-EXCLUDED-SAMPLES`), the arm's `lab_loss_state_weights` are the state weights of those views; every other view uses `analysis_spec.state_weights_by_arm`.
- `comparisons`: each arm compared with its matched control (`comparison_reference_arms`), or with the reference arm when it has none. `reference_comparisons` compares with the reference arm only the arms whose matched control is another arm.
- `rankings` and `rankings_available`; `comparison_requirements`, each frozen requirement with its outcome and each requested view's comparison status; and `comparison_families`, each family's requirements, status and rankings.
- `scenario_contributions`: each scenario's EAL and share of the pooled EAL, with the pooled EAL that no scenario carries; then `producer_provenance` and `execution_context`.
- `reasons`: every reason in the file is a code, the first 12 hexadecimal digits of the SHA-256 of the reason's UTF-8 text, and `reasons` maps each code to its text.

The diagnostics file holds `schema_version`, the `analysis_sha256` of its results and its own `reasons` table. Its exhibits are:

- `sensitivity_summary`, whose tornado the run draws in `tornado.svg` ([context-bound comparisons](#context-bound-comparisons) lists what it holds);
- `capability_scenarios`, for public studies ([reading results](research-results.md#capability-conditioned-results));
- `small_event_aggregation` (`NUM-SMALL-EVENTS`);
- `tail_gate`: each arm's rounds, years and withheld statistics;
- `scenario_groups`: the scenario EALs added up by reporting domain and by each facet on which a scenario has one value ([scenario contributions](../methodology.md#scenario-contributions));
- `workload`.

Under `arms` it holds each arm's view diagnostics: the mean and tail diagnostics and the per-state records.

### Results file versions

`schema_version` is an integer that names the layout of `results.json` and of its diagnostics file; it is 1. It increases with every change to either file's fields, their types or their meaning, including an added field. Readers in this repository accept only the current version: `load_results`, and so `results summary` and the reading of an export, refuse another one, a file that does not match its schema and a file whose `analysis_sha256` is not the digest of its `analysis_spec`. Results are derived data with no migration between versions: `catmodel results replay` derives current results from the run's capture, and the producer code pinned in an older file's provenance reads that file. `export.json` has its own version in `format` (`cat.results/1`); its native results carry their own `schema_version`.

`contracts/results/results.schema.json` and `contracts/results/results.diagnostics.schema.json` are the JSON Schema (draft 2020-12) documents of the two files at the current version. The wheel and the source archive ship them, and `scripts/generate_results_schemas.py` regenerates them from the TypedDicts of `catmodel.contracts.results`. Every record is closed, so a misspelt or unknown field fails. A few values stay open: each evidence record's `acquisition`, and the frequency estimate's `frequency_collection`, `eal_crosscheck` and `hierarchy` (with `hierarchy_pool`), which are the collection's own validation summaries. A schema fixes a file's shape, not its values: `load_results` also checks the analysis digest, the reasons table's codes and that the diagnostics file belongs to its results, and loading an export requires its results to reproduce from its capture.

### Readable summary

`catmodel results summary --results <results.json> --output <new-directory>` writes `summary.md` and `summary.csv` from one results file and the diagnostics file beside it, without recomputing any statistic; its `--help` lists what they hold. `summary.md` gives, in order:

- The study and a headline table: the EAL of societal harm (`welfare`) and of each named lab's economic loss (`lab_loss::<lab_id>`), with their statuses. Where the plan requests neither view, the table gives the EAL of each of `gross`, `net_resource_cost` and `financial` that it requests.
- The EAL by scenario and, for scenarios of the library, by reporting domain.
- Reporting domains by [severity tier](taxonomy.md#severity-tiers): each domain's EAL beside its expected annual numbers of incidents of at least USD 1 billion and of at least USD 100 billion under the run's laws, where the result holds the `large_loss_anchor` exhibit.
- Aggregate (AEP) and occurrence (OEP) losses at 1-in-10, 1-in-100, 1-in-200 and 1-in-250 (levels 0.9, 0.99, 0.995 and 0.996), under headings marked illustrative.
- Respondent dispersion: the lowest, weighted-median and highest respondent EAL of each pooled headline view, and the share of the pooled EAL that its largest respondent carries.
- For a contextual setup, each leaf's direct EAL judgment beside the EAL that its count and severity answers imply and its EAL in the run; the EAL effect of each kind of follow-up call and of the taxonomy parents' pools; and the exhausted calls, the excluded samples and each model and scenario that the model does not answer, with the models whose answers stand in.
- The result's `limitations`, without the model-wide items that do not apply to its study.

A withheld value is shown in parentheses. A value missing from the results file is a dash with its status, never zero.

`summary.csv` has one row for each reported value or label, in the columns its header names. `value` holds the number, a withheld one included, and is empty when the statistic is unavailable or not requested, or is a label. `label` holds a categorical result or a qualifier of the value (`lower_bound` for a group EAL or tier count that sums only its available scenarios, `flagged` for a plausibility share or count), and `status` is `available`, `withheld`, `unavailable` or `not_requested`.

The summary's plausibility checks are two report-only tables with review flags (`NUM-PLAUSIBILITY`), both in section `plausibility` of `summary.csv`. The first gives each scenario's welfare EAL and the total as shares of world output. The second, for a contextual setup, gives the expected annual number of incidents of at least USD 1 billion in each scenario that asks that count and in total, as the respondents stated it, after pooling and under the run's laws; a scenario at or above 0.1 a year and a total at or above 1 a year are flagged.

## Portable results and conditional distributions

`catmodel results export --setup <setup> --capture <run/capture> --output <new-directory>` reduces the capture under the setup's plan and writes `export.json` beside copies of the native setup and capture, the results and the three capability artifacts, `capability_scenarios.json`, `capability_scenarios.csv` and `capability_nodes.csv`. The export's results are `results.json` and a diagnostics file that holds the exhibits and no view diagnostics (its `arms` is empty), which `results replay` rederives from the exported capture. `export.json` records the relative path and SHA-256 of each native artifact (`source`) and of each capability artifact (`outputs`).

`--results <results.json>` exports a results file in place of that reduction: one that `run` or `results replay` derived from the same setup and capture, such as a replay with `--weights` or `--level`, with its diagnostics file beside it. The export copies `results.json` unchanged. An edited file, or one from another setup or capture, is refused and no export is written.

The capture and every setup file the export holds are unchanged copies. By default the setup's copy leaves out the files of an imported setup that hold a captured prompt, a response or the answers parsed from the responses: each collection's `calls/` and `contextual-risk.json`, and any other file under `evidence/captured/` that is neither a source bundle's nor one the study and its collections write about themselves (the study plan, forecast, quadrature and fitted trend; each instrument, collection plan, call settings and parser identity). `omitted-evidence.json`, beside the copy's manifest, lists each omitted file by its path and the SHA-256 the manifest records, so the holder of the setup can check that it is the one the export was made from. The copy loads as a setup, for `results replay` and `ConditionalCapture` as for the export's own check: a setup holds all of those files or, with that record, none of them, and every file it holds is checked either way. `--include-answers` copies the setup whole, and a setup without captured answers, such as one from `setup build`, is always copied whole. An export is made from the whole setup, not from a copy without its answers.

Whenever an export is written from a results file, or loaded, its results must reproduce from its capture under the running reducer: the same structure, statuses, reasons, integers and digests, and every number within a relative 10⁻⁹, because another CPU or BLAS build changes the last bits of long sums (`_scale_of` in `results_export.py` gives each number's scale). An export whose results no longer reproduce is made again from its capture. `catmodel.results.results_export.load_results_export(directory)` also checks every checksum and re-derives the index and each capability artifact from the native data. The chain summary is the one value computed from the captured answers: an export without them states it as computed when the export was made, and `load_results_export(directory, answers=<setup>)` rederives it from the omitted files, each checked against its recorded SHA-256. The evidence an export holds is copied without redaction, and an export is not clearance to redistribute it ([limitation 11](limitations.md#11-captured-evidence-can-carry-third-party-rights)).

The index exposes societal harm (`welfare`) and each named lab's economic loss (`lab_loss::<lab_id>`) as peer series, with unavailable entries when either is missing; insurance payment (`financial`) is a different observable. Display EP points use strict `P(loss > threshold)` in native units, at 0 and at each percentile of the series' simulated annual losses, at most 102 points. They are not the full distribution, which the native arrays and state weights retain. Within a native arm and state, the societal and lab arrays share annual rows; do not join separate marginal curves or align row numbers across states or arms.

For a contextual setup, `chain_summary` is the frequency-chain panel, per scenario and source status, at the public study's center trajectory node (progress ratio 1) or a fixed-anchor context's center anchor. Each value is the median of its per-case value across the respondents and samples whose cases the run keeps, each stored case once (`ContextualChainSummary` in `catmodel.contracts.results` lists the fields), so `case_count` counts the answers the run uses (`POOL-EXCLUDED-SAMPLES`, `POOL-UNANSWERED-SCENARIOS`).

A `RunSetup.conditional_contexts` entry (`ConditionalContext` in `catmodel.contracts.conditional`) holds a complete conditional state mixture for every integer of its range and every required arm, so a point at zero forecast probability still needs its kernel. `ConditionalCapture(setup, capture_directory).kernel_at(context_id, integer, arm_id)` checks the native capture and returns the conditional mixture for one score. It selects authored kernels and neither interpolates between scores nor infers interventions: outside the authored range lookup fails with `out_of_modeled_range`, and a noninteger score fails with `integer_required`. The export labels a context supported only when every integer and arm kernel has both peer distributions as physical joint samples. `config/setups/stipulated-conditional` illustrates the mechanism with stipulated numbers.

## Captured evidence

Captured context-bound evidence enters a setup through `catmodel setup import`. `--study <public-study.json>` replays a public study's paired trajectory captures into one setup, and `--run-directory <contextual-run>` replays one fixed-anchor capture for conditional what-if analysis. Both validate the captured questions, acquisition treatment, every raw attempt, the source bundle that each capture keeps and the fitted-law dependencies, before compiling the conditional annual incident laws. Collected evidence has no financial inputs, so the setup carries only the economic views. The [runbook](../runbook.md#2-context-bound-labdeployment-questions) gives the collection and intake commands.

### Context-bound comparisons

`catmodel setup import --study` freezes every catalog family in `catmodel.setup.sensitivity_catalog` as a comparison requirement. By default it selects `public_forecast`, `model_pooling_leave_one_out`, `tail_shape`, `uncapped_severity`, `exposure_scale` and `safeguard_level` (`DEFAULT_CONTEXT_BOUND_FAMILIES`); the last two stay unavailable until their variant studies are imported with `--variant-study` ([runbook](../runbook.md#hypothetical-frontier-lab-study)). `--comparison-family` names another selection, and `--comparison-family all` selects the whole catalog, which includes `lab_loss_cap` (three runs, lab-loss view only) and `lab_loss_provider_only` (one run, lab-loss view only). Every family not selected is recorded unavailable, with a reason that names how to select it. The register challenges that no context-bound setup executes, such as the reference-held capability response (`OBS-CAUSAL`), are frozen as unavailable requirements, which `coverage.sensitivity_families` lists with kind `register_challenge`.

Reweighting arms keep every conditional law and change only joint-state weights, so they reuse the reference draws. Simulated arms recompile the captured answers under one change applied to every node in scope, so each costs at most one reference-equivalent run. A node that a change cannot represent, such as a shape shift beyond its operating bound, is recorded unavailable for that arm and keeps its reference law; a node that the change leaves numerically unchanged is inapplicable. Each joint state is identified by its trajectory and respondent selection, not by the setup ID, and its streams are seeded from the plan seed and that identity, so two imports of the same captures simulate identical reference draws.

The sensitivity summary holds the tornado of EAL effects, the families not assessed, the `dependence_bracket` of executed against within-state comonotone tails, and these exhibits:

- `trajectory_quadrature` (public studies): for the reference and each forecast arm, the EAL under the full trajectory rule and under its embedded lower-order rule on the same nodes, with an `indicator` ([methodology](../methodology.md#trajectory-quadrature)). Each arm's `by_node` rows give a node's `state_eal_sd`, the standard deviation of its samples' EALs. It is null with a `state_eal_sd_reason` at a node of one sample and at a node where a sample reads a donor's answers (`POOL-UNANSWERED-SCENARIOS`).
- `frequency_estimate` (contextual setups; [methodology](../methodology.md#event-populations-and-frequency)): the reference EAL under the final pooled count beside the direct count alone, the chain count alone, the count before each of the collection's three follow-up calls (`follow_up_effects`, `follow_ups`) and the two ends of the taxonomy parents' pool weight (`before_hierarchy`, `hierarchy_parents_only`). It also holds the `eal_crosscheck` status counts and cases, with each leaf's direct and implied EAL means (`FREQ-EAL-CROSSCHECK`). It has no tail statistics.
- `hierarchy_pool` (instruments with taxonomy-parent questions; `HIER-CATEGORY-POOL`): per parent, its height and the weight of its own answer, the case counts by status, every case's pool with their medians across cases, and the remainder as an `estimated_unsimulated` EAL that no total includes.
- `large_loss_anchor` (contextual setups; `SEV-LARGE-LOSS-ANCHOR`): the expected annual numbers of incidents of at least USD 1 billion and USD 100 billion as stated, as pooled and as modeled, and each view's EAL beside the analytic alternatives ([methodology](../methodology.md#sensitivity-validation-and-communication)).
- `respondent_sampling` (context-bound setups; `NUM-RESPONDENT-SAMPLING`): each welfare, gross, lab-loss and source-status EAL with its respondent-sampling standard error, and each arm's change against its control with its paired standard error and `sampling_z` ([methodology](../methodology.md#pooling-and-parameter-uncertainty)). An EAL or a change in which a state with weight reads a donor's answers (`POOL-UNANSWERED-SCENARIOS`) is `unavailable` with its reason. The standard error of a lab-loss view or a gross view is that of the samples it holds (`POOL-EXCLUDED-SAMPLES`); `groups`, `samples` and `smallest_group` count the reference arm's samples.
- `excluded_samples` (contextual setups; `POOL-EXCLUDED-SAMPLES`): every call that exhausted its validation attempts, with the cause of its last attempt (`validation`, `refusal` or `output_limit`); every direct answer that declares the lab's loss unavailable, with the samples left out of the lab-loss and gross views for it or the guard that withholds those views (`lab_loss_unavailable`); the excluded samples, each with the leaves it lacks; their shares against the frozen `max_excluded_sample_share`; and the renormalized weights. Where a model does not answer a scenario, `unanswered_scenarios` (`POOL-UNANSWERED-SCENARIOS`) lists each such model and leaf (`pairs`), each such leaf's answering models with their realized shares of its pool (`by_leaf`), and the number of leaves that one model answers (`leaves_on_one_model`). A variant study's record adds `matched_control`: whether it differs from its matched control in the scenarios or the donors.
- `plausibility` (`NUM-PLAUSIBILITY`): each scenario's welfare EAL and the total as shares of the governed world-output reference for the study year, with `flagged_scenarios`.
- `eal_parameter_band` (`NUM-EAL-PARAMETER-BAND`): for each welfare, gross and lab-loss view whose EAL is an analytic mean, p5, p50 and p95 of the EAL with each rank group's count law held at one rank for every year, under `independent` and `comonotone` ranks. A lab-loss view or gross whose band is computed at its own weights records its `states` and its `incomplete_epistemic_groups`. A view in which a state with weight reads a donor's answers (`POOL-UNANSWERED-SCENARIOS`) is `unavailable` with its reason, and where that leaves no view with a band the exhibit is `unavailable` with the same reason.

Context-bound import freezes the starting years per state, each arm's cap on simulated state-years, the work allowances and plan seed 42; the [runbook](../runbook.md#4-build-a-setup-and-run-it) gives the values and how to set others. `setup inspect` reports the frozen and reused state-year workload before a run, with each state's work limits (`max_work_per_state`) and the `reference_work_multiple`.
